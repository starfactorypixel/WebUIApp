# Протокол подключения к ESP32 (шлюз CAN): руководство разработчика

Документ описывает всё, что нужно, чтобы на любом языке написать программу, которая подключается к ESP32 по UART и работает с ним: кадры L3, сеанс, сообщения внутри кадра, подписки и команды объектам CAN, настройки блоков, скрипты. Тестовые векторы (раздел 13) проверены двумя независимыми реализациями.

Все многобайтные числа — little-endian, структуры без выравнивания. «От ESP» и «к ESP» — направление кадра. ESP в протоколе — **сервер**: он объявляет себя beacon'ами и держит сеанс. Ваша программа — **клиент**, она подключается к ESP.

## 1. Коротко

```
UART (поток байт) → кадр L3 (подпись AES-GCM) → DATA → [len][fId][…] [len][fId][…] … → прикладные сообщения
```

- ESP периодически шлёт **beacon** — подписанный кадр с серийным номером (SN) и именем. Клиент находит ключ по SN, проверяет подпись и сразу отправляет **accept**. ESP отвечает своим accept: сеанс открыт, можно слать прикладные данные.
- Каждый кадр подписан AES-256-GCM (формат SIGN) или зашифрован (ENCRYPT). Повтор отсекается растущим номером пакета N, кадр чужого сеанса — подписью.
- В одном кадре — одно или несколько сообщений, **перед каждым его длина**. Разбор не зависит от типа сообщения.
- Прикладные сообщения: подписка на объекты CAN (`CanSub`), сообщения объектов (`CanMsg`), скрипты (`Script`), информация о блоках (`BlockInfo`).

Клиенту нужны:
- ключ устройства (32 байта) и его SN — таблица «SN → ключ»;
- формат канала (SIGN или ENCRYPT) и размер DATA канала (`DATA_MAX`) — их нужно знать заранее, как настройки порта;
- AES-256-GCM, CRC-16/XMODEM, CRC-32, криптостойкий генератор случайных чисел;
- последовательный порт.

## 2. Транспорт: UART

- Скорость — 921600, 8N1, без управления потоком (если в вашем устройстве не задано иначе).
- Вход — поток байт. Кадры идут вплотную, между ними может быть текст отладочного лога ESP.
- **Парсер потока:**
  1. найти `0x50 0x58`;
  2. прочитать заголовок (6 байт), взять LEN; LEN больше `12 + DATA_MAX + 16` — кандидат ложный;
  3. дождаться `8 + LEN` байт и проверить CRC;
  4. кандидат ложный (LEN велик, CRC не сошёлся) — сдвинуться на **один байт** от начала кандидата и искать снова: внутри мог начаться настоящий кадр;
  5. кадр собирается дольше **200 мс** — сигнатура была ложной, тоже сдвиг на один байт.
- Байты вне кадров — текст ESP; его можно показывать как лог устройства.
- Исходящие кадры можно отправлять вплотную, пауза не нужна.
- Совет: если кадр с правильным началом (`50 58 02`) отброшен из-за слишком большого LEN, сообщите об этом оператору — почти наверняка у ESP другой `DATA_MAX`, и иначе такие кадры теряются молча.

## 3. Кадр

| Смещение | Размер | Поле | Содержимое |
|---|---|---|---|
| 0 | 2 | HEAD | `0x50 0x58` ('P' 'X') |
| 2 | 1 | CTRL0 | биты 0–3: версия = 2; бит 7: направление, 0 — от ESP, 1 — к ESP; биты 4–6 = 0 |
| 3 | 1 | CTRL1 | биты 0–2: формат; биты 3–7 = 0 |
| 4 | 2 | LEN | длина PAYLOAD |
| 6 | LEN | PAYLOAD | IV(12) · DATA · TAG(16) |
| 6 + LEN | 2 | CRC | CRC-16/XMODEM от байт 0 … 5 + LEN |

- CTRL0: у кадра клиента `0x82`, у кадра ESP `0x02`.
- Формат: **SIGN = 1** — DATA открыты, кадр подписан; **ENCRYPT = 3** — DATA зашифрованы. Формат задан на канал. **Beacon всегда SIGN.** Значит, на канале ENCRYPT клиент принимает от ESP SIGN (beacon) и ENCRYPT, а отправляет только ENCRYPT.
- CRC-16/XMODEM: полином 0x1021, начальное значение 0, без отражения, без финального XOR. `"123456789"` → `0x31C3`. Считается последним, после подписи. Это фильтр битых кадров, а не защита.

**Размеры** (от `DATA_MAX` канала; сейчас на UART — **128**):

| Величина | Формула | При DATA_MAX = 128 |
|---|---|---|
| DATA | 0 … DATA_MAX | ≤ 128 |
| LEN (PAYLOAD) | 12 + DATA + 16 | 28 … 156 |
| Кадр | 6 + LEN + 2 | 36 … 164 |
| Сообщение (fId + данные), `MSG_MAX` | min(DATA_MAX − 1, 255) | 127 |

## 4. IV и номер пакета N

IV — первые 12 байт PAYLOAD.

| Байты IV | Поле | Кадр ESP | Кадр клиента |
|---|---|---|---|
| 0–2 | epoch, 24 бита | старшая часть N ESP | старшая часть своего N |
| 3 | instance | instance ESP | **instance ESP XOR 0xFF** |
| 4–7 | counter, 32 бита | младшая часть N ESP | младшая часть своего N |
| 8–11 | random | **идентификатор сеанса ESP** | 4 случайных байта клиента, новые при каждом подключении |

N = epoch · 2³² + counter (56 бит; храните в 64-битном целом).

- Каждая сторона ведёт свой N и увеличивает его **перед** каждым своим кадром. Переполнение counter переносится в epoch (`1:0xFFFFFFFF` → `2:0`). N = 2⁵⁶ − 1 — отправлять больше нельзя.
- Стартовый N клиента при подключении — N из beacon.
- Принимается только кадр ESP с N **больше** последнего принятого.
- instance клиента всегда берётся из IV beacon (`XOR 0xFF`), не зашивается в код: он разводит IV клиента и ESP при одинаковом N. Повтор IV при одном ключе ломает GCM.
- random — из криптостойкого генератора.

## 5. Подпись

AES-256-GCM: ключ 32 байта, IV 12 байт как есть, тег 16 байт.

| Кадр | AAD | Шифруется | PAYLOAD |
|---|---|---|---|
| Клиента, SIGN | заголовок(6) + IV(12) + DATA + **сеанс ESP(4)** | ничего | IV + DATA + TAG |
| Клиента, ENCRYPT | заголовок(6) + IV(12) + **сеанс ESP(4)** | DATA | IV + шифротекст + TAG |
| ESP, SIGN | заголовок(6) + IV(12) + DATA | ничего | IV + DATA + TAG |
| ESP, ENCRYPT | заголовок(6) + IV(12) | DATA | IV + шифротекст + TAG |

**Сеанс ESP** — байты 8–11 IV того beacon, по которому клиент подключился. В кадры клиента эти 4 байта в эфир не идут, только в подпись: кадр клиента действителен только в своём сеансе ESP.

**Сборка кадра клиента:**
1. LEN = 12 + len(DATA) + 16; записать заголовок (он входит в AAD).
2. N += 1; IV = epoch(3) · instance клиента · counter(4) · random клиента(4).
3. AAD по таблице, в конце — сеанс ESP. SIGN: тег от пустого открытого текста; ENCRYPT: шифротекст + тег.
4. CRC по байтам 0 … 5 + LEN, дописать в конец.

**Проверка кадра ESP**, по порядку; любая неудача — отбросить кадр молча:
CRC → версия = 2 → направление «от ESP» → формат (SIGN или формат канала) → LEN ≥ 28 → тег → instance → сеанс → N.
Сеанс проверяется **раньше** N: по нему клиент узнаёт о новом сеансе ESP, а N нового сеанса может быть меньше прежнего. Последний принятый N меняется только после всех проверок.

## 6. Сеанс

Два состояния: **поиск** и **сеанс**. Состояние живёт только в памяти: после перезапуска клиента или потери связи — снова поиск.

| Переменная | Смысл |
|---|---|
| key | ключ, найденный по SN |
| esp_instance | IV[3] из beacon |
| my_instance | esp_instance XOR 0xFF |
| esp_session | IV[8..11] из beacon |
| tx | свой N — номер последнего отправленного кадра |
| esp_rx | N последнего принятого кадра ESP |
| random | своя случайная часть IV |
| interval | интервал beacon из последнего beacon, мс |
| last_rx | время последнего валидного кадра ESP |
| accepted | ESP ответил accept |

**Поиск.**
1. Нужен кадр SIGN «от ESP», у которого **первое** сообщение DATA — beacon.
2. По SN найти ключ. Нет ключа — сообщить оператору (SN и имя — непроверенные данные, показывать с пометкой).
3. Проверить тег. Не сошёлся — неверный ключ или подделка.
4. Подключиться: key; esp_instance = IV[3]; my_instance = esp_instance XOR 0xFF; esp_session = IV[8..11]; tx = esp_rx = N beacon; random = 4 новых байта; interval; last_rx = сейчас; accepted = false.
5. **Сразу отправить accept** (DATA `01 01`).

**Сеанс.**
- **Отправка** прикладных данных — только при accepted = true.
- **Приём:** проверки раздела 5; после них esp_rx = N, last_rx = сейчас; разобрать DATA (раздел 7).
- **Accept от ESP** → accepted = true. **Сразу подписаться заново на все нужные объекты**: подписки живут только в сеансе, после перезапуска ESP их нет.
- **Ping от ESP** → сразу ответить кадром с DATA `01 05`, не дожидаясь приложения.
- **Beacon с тем же сеансом** → обновить только interval.
- **Кадр с другим сеансом** (тег верный): если в нём beacon — ESP перезапустился или закрыл сеанс, подключиться заново по этому beacon (шаги 4–5 поиска), даже если его N меньше esp_rx. Иначе кадр отбросить.
- **Потеря связи:** с last_rx прошло больше **3 × interval** → назад к поиску.
- **Порт закрылся** → выбросить недособранный кадр, назад к поиску.

Отправка и приём меняют одно состояние (tx). Если они в разных потоках — один мьютекс на оба, иначе два кадра уйдут с одним N.

## 7. Сообщения внутри DATA

DATA — сообщения подряд, перед каждым его длина:

```
[len u8][fId][данные…] [len u8][fId][данные…] …
```

- `len` — число байт **после** него (fId + данные), 1 … `MSG_MAX`. Сам `len` не считается.
- Формат один для всех сообщений, служебных тоже: accept — `01 01`, ping — `01 05`.
- В одном кадре может быть сколько угодно сообщений любых типов в любом порядке. Пустой DATA допустим.

**Разбор:**

```
while left > 0:
    n = p[0]
    if n == 0 or 1 + n > left: break       // неверный len — остаток DATA пропустить
    handle(p[1 .. n])                      // сообщение: fId + данные, длина n
    p += 1 + n; left -= 1 + n
```

- Неизвестный fId пропускается: следующее сообщение находится по len.
- **Минимальная длина.** Перед разбором полей сообщения проверьте, что оно не короче своего заголовка (таблица раздела 8, колонка «мин.»). Короче — отбросить это сообщение и продолжить разбор DATA.

**Сборка.** Сообщения складываются в DATA подряд с байтом длины. Не помещается в DATA_MAX — отправить накопленное отдельным кадром и начать новый. **Упаковывайте:** большинство прикладных сообщений — 4–10 байт, а кадр добавляет 36 байт. Что относится к одному действию (команда нескольким объектам, подписка и отписка при смене экрана, чтение всех параметров блока) — отправляйте одним кадром.

## 8. Типы сообщений

| fId | Имя | Направление | Длина (fId + данные) | Мин. |
|---|---|---|---|---|
| 0x00 | Beacon | ESP → | 12 + длина имени | 12 |
| 0x01 | Accept | ⇄ | 1 | 1 |
| 0x05 | Ping | ESP → запрос, → ESP ответ | 1 | 1 |
| 0x0A | BlockInfo | ESP → | 32 | 32 |
| 0x12 | CanSub | → ESP | 2 + 2 × count | 2 |
| 0x1B | Script | ⇄ | запрос ≥ 2, ответ ≥ 3 | 3 |
| 0x35 | CanMsg | ⇄ | 4 + len | 4 |

### 8.1 Beacon (0x00)

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 1 | fId = 0x00 |
| 1 | 2 | interval, мс |
| 3 | 8 | SN — по нему ищется ключ |
| 11 | 1 | длина имени, 0–32 |
| 12 | … | имя, UTF-8, без завершающего нуля |

Идентификатор сеанса лежит не в DATA, а в IV beacon. Beacon с длиной имени больше 32 или короче заявленного — битый.

### 8.2 CanSub (0x12): подписка и отписка на объекты CAN

```
[0x12][count u8][id u16] × count
```

- `id` — объект CAN (obj, 11 бит). **Бит 0x8000** у id — отписка; без него — подписка. В одном сообщении могут быть и те, и другие; кладите сначала отписку, потом подписку.
- `count` ≤ 255 и ≤ (MSG_MAX − 2) / 2 (при DATA_MAX 128 — 62). Больше id — несколько сообщений CanSub, по возможности в одном кадре.
- На **каждую подписку** ESP отвечает текущим состоянием объекта — CanMsg с CAN-fId 0x65 (8.4). Повторная подписка безвредна и служит способом запросить состояние ещё раз.
- Подписки действуют до конца сеанса. Новый сеанс (раздел 6) — подписаться заново.
- Если у клиента несколько потребителей данных (например, несколько окон), ведите учёт сами: подписывайте объект в ESP при каждом новом потребителе (он сразу получит состояние), а отписывайте, только когда объект больше не нужен ни одному.

Пример: отписка 0x0164, подписка 0x0110 и 0x0112 — `12 03 64 81 10 01 12 01`.

### 8.3 CanMsg (0x35): сообщение объекта CAN

```
[0x35][id u16][len u8][bytes × len]
```

Одинаково в обе стороны. `id` — obj; `bytes` — полезная нагрузка CAN, её первый байт — **CAN-fId** (тип CAN-сообщения; не путать с fId сообщения L3). Проверка: длина сообщения = 4 + len.

От ESP приходят сообщения объектов, на которые клиент подписан, и ответы на его команды.

Пример: два состояния в одном DATA от ESP — `07 | 35 10 01 03 65 d2 04` и `07 | 35 12 01 03 61 08 02` (obj 0x0110: CAN-fId 0x65, значение 1234; obj 0x0112: CAN-fId 0x61, значение 520).

### 8.4 CAN-fId

| CAN-fId | Направление | Данные после CAN-fId | Смысл |
|---|---|---|---|
| 0x01 | → ESP | значение | SET: установить |
| 0x02 | → ESP | — | TOGGLE: переключить; объект сам решает, во что |
| 0x03 | → ESP | — | ACTION: однократное действие |
| 0x11 | → ESP | — | запросить все значения объекта-набора (см. ниже) |
| 0x0A | → ESP | counter u8, значение | RealTime: «живое» управление (см. ниже); ответа нет |
| 0x61 / 0x62 / 0x63 | ESP → | значение | периодическое значение по таймеру; тип таймера уже классифицирует его: норма / предупреждение / критично |
| 0x65 | ESP → | значение | текущее состояние: ответ на **любую** команду и на подписку |
| 0x37 | ⇄ | см. 8.5 | настройки блока |

- Тип значения (uint8, int16, uint32, …) протокол не передаёт: он известен из описания объекта. Числа little-endian.
- **Управляемые** объекты (например, «фары») шлют сообщение только в ответ на команду или подписку; **индикаторы** (напряжение) — по таймеру.
- **Подтверждение команды** — 0x65 от объекта. Для SET значение в ответе должно совпасть с отправленным. Рекомендуемое ожидание — около 1 с; повторять команду автоматически не стоит — решение за пользователем. Протокол не связывает ответ с конкретной командой: если два ожидания на один obj идут одновременно, ответ может быть засчитан не той команде.
- **RealTime (0x0A)** — управление, которое действует, только пока его держат (газ, руль). Пока держат — клиент шлёт текущее значение периодически (например, раз в 100 мс); отпустили — одно сообщение со значением покоя. `counter` — uint8, свой у каждого obj, +1 на каждое сообщение этому obj (после 255 — 0): по нему устройство видит пропуски и повторы. Ответа нет; если сообщения перестали приходить, решение — за устройством. Тот же механизм возможен и через SET (0x01) без счётчика. CAN-fId 0x0A не связан с сообщением L3 BlockInfo (тоже 0x0A): это разные уровни.
- **Объект-набор** (ячейки АКБ, датчики): каждое сообщение — `[CAN-fId][номер u8][значение]`, обновляет одну позицию; 0x11 просит прислать все.
- **Баланс ячеек:** `[CAN-fId][min u16][max u16][номер min u8][номер max u8]`.

### 8.5 Настройки блока (CAN-fId 0x37)

Идут в CanMsg на **obj настроек** блока: baseID блока (из BlockInfo) + смещение настроек (для текущих блоков — 1). Параметры блока (номер, тип значения, границы) — из описания типа блока (по hw_type из BlockInfo); протокол их не передаёт.

| Запрос | Ответ | Смысл |
|---|---|---|
| `37 01 id` | `37 01 id значение` | чтение параметра |
| `37 02 id значение` | `37 02 id значение` | запись параметра |
| `37 03` | `37 03` | сохранить всё и перезагрузить блок (ответ может не прийти, если блок перезагрузился раньше) |
| — | `37 04 код` | ошибка (номера параметра в ответе нет) |

Подпишитесь на obj настроек перед запросами, чтобы получить ответы, и отпишитесь, когда настройки закрыты. Чтение всех параметров — пачкой CanMsg в одном кадре.

### 8.6 BlockInfo (0x0A)

Каждый блок периодически присылает 32 байта о себе; подписка не нужна.

| Байты | Поле |
|---|---|
| 0 | fId 0x0A |
| 1–2 | baseID u16 |
| 3 / 4 / 5 / 6 | hw_type / hw_ver / sw_ver / can_ver |
| 7–14 | SN блока, 8 байт |
| 15–21 | features, 7 байт |
| 22–25 | uptime u32, мс |
| 26–27 | напряжение u16, мВ |
| 28–29 | ток u16, мА |
| 30 | температура i8, °C |
| 31 | флаги ошибок |

## 9. Скрипты (Script, 0x1B)

ESP хранит до 2048 скриптов (id 0 … 0x7FF), каждый до 4080 байт. Скрипты лежат во флеш-памяти ESP; исполняются копии, загруженные в оперативную память (PSRAM).

**Источник правды — загруженные в память скрипты** (то, что исполняется): INFO, READ, LIST, ENABLE работают с ними. **WRITE_END и DELETE меняют только флеш-память** и ставят признак «нужна перезагрузка»; старые скрипты исполняются, пока клиент не пришлёт RELOAD. Признак приходит в каждом ответе LIST (`reload_needed`).

```
Запрос:  [0x1B][cmd]           [поля…]
Ответ:   [0x1B][cmd | 0x80][status i8][поля…]
```

- Ответ есть на **любой** запрос с `cmd`. `status`: 0 — успех, отрицательный — ошибка. При ошибке после status идёт `id` (у WRITE — `id, offset`); если запрос не разобран (BAD_REQUEST) — полей нет.
- Своей длины у сообщения нет: длина данных WRITE и READ — из `len` сообщения.
- **CRC-32** — стандартный (как zlib): полином 0xEDB88320, начальное 0xFFFFFFFF, финальная инверсия; `"123456789"` → `0xCBF43926`. Только по данным скрипта.
- Запросы — **по одному**: отправить, дождаться ответа с тем же cmd. Рекомендуемое ожидание — 1,1 с на шаг, на RELOAD — 5,5 с (он читает всю флеш-память).

| cmd | Поля запроса | Поля ответа | Смысл |
|---|---|---|---|
| 0x01 INFO | `id u16` | `id u16, length u16, crc32 u32, flags u8` | скрипт в памяти: длина, CRC данных, флаги |
| 0x02 DELETE | `id u16` | `id u16` | стереть во флеш-памяти (есть скрипт или нет — OK); в памяти — до RELOAD |
| 0x03 WRITE_BEGIN | `id u16, length u16` | `id u16, max_chunk u16` | начать запись; ESP сообщает свой предел куска |
| 0x04 WRITE | `id u16, offset u16, data…` | `id u16, offset u16` | кусок данных |
| 0x05 WRITE_END | `id u16, crc32 u32` | `id u16` | проверить длину и CRC, записать во флеш-память |
| 0x06 READ | `id u16, offset u16, max_len u16` | `id u16, offset u16, data…` | кусок скрипта из памяти (и отключённого) |
| 0x08 RELOAD | — | `count u16` | загрузить все скрипты из флеш-памяти в память; снимает «нужна перезагрузка» |
| 0x0A ENABLE | `id u16, on u8` | `id u16, flags u8` | включить или отключить; держится до перезапуска ESP, RELOAD не сбрасывает |
| 0x0C LIST | `from u16` | `reload_needed u8, next u16, {id u16, length u16, flags u8} × N` | скрипты в памяти с id ≥ from; next = 0xFFFF — конец, иначе спросить с from = next |

**flags:** `0x02` — загружен в память, `0x04` — включён.

| status | Имя | Когда |
|---:|---|---|
| −1 | BAD_REQUEST | неизвестная команда или неверная длина запроса |
| −2 | BAD_ID | id ≥ 2048 |
| −3 | NOT_FOUND | скрипт не загружен в память |
| −4 | TOO_LONG | длина больше 4080 |
| −5 | BAD_OFFSET | кусок с дыркой или за концом; чтение за концом |
| −6 | NO_WRITE | WRITE / WRITE_END без WRITE_BEGIN для этого id |
| −7 | CRC_MISMATCH | CRC не совпал с принятыми данными |
| −8 | INCOMPLETE | WRITE_END, а принято меньше length |
| −9 | FLASH_ERROR | после записи заголовок во флеш-памяти не тот |

**Размеры кусков** — от MSG_MAX:
- запись: кусок ≤ min(max_chunk из ответа WRITE_BEGIN, MSG_MAX − 6);
- чтение: просить ≤ MSG_MAX − 7; ESP отдаёт ≤ min(max_len, свой предел, остаток);
- LIST: ESP кладёт до (MSG_MAX − 6) / 5 записей.

**Последовательности:**
- **Чтение:** INFO → READ с offset = 0, n, 2n … до length → сверить CRC-32 прочитанного с crc32 из INFO.
- **Запись:** WRITE_BEGIN(length) → WRITE кусками по возрастанию offset (повтор куска безопасен) → WRITE_END(crc32) → скрипт во флеш-памяти; исполняться начнёт после RELOAD. Новый WRITE_BEGIN отменяет незаконченную запись.
- **Список:** LIST(0) → LIST(next) → … пока next ≠ 0xFFFF.

Пример (в DATA, до `|` — len): INFO id 7 — `04 | 1B 01 07 00`; ответ — `0C | 1B 81 00 07 00 0A 00 7A 0E 9C A7 06` (длина 10, CRC 0xA79C0E7A, загружен и включён).

## 10. Псевдокод клиента

```
// ---------- кадр
build_frame(fmt, data):
    len = 12 + size(data) + 16
    header = [0x50, 0x58, 0x82, fmt, len & 0xFF, len >> 8]
    tx += 1
    iv = le24(tx >> 32) + [my_instance] + le32(tx & 0xFFFFFFFF) + random
    if fmt == SIGN:    payload = iv + data + gcm_tag(key, iv, aad = header + iv + data + esp_session, plaintext = empty)
    if fmt == ENCRYPT: payload = iv + gcm_encrypt(key, iv, aad = header + iv + esp_session, plaintext = data)   // шифротекст + тег
    body = header + payload
    return body + le16(crc16_xmodem(body))

// ---------- DATA
pack(messages):                         // каждое: fId + данные
    out = []
    for m in messages: out += [size(m)] + m
    return out                          // size(out) ≤ DATA_MAX — иначе разбить на кадры

// ---------- приём кадра (CRC уже проверен парсером потока)
on_frame(f):
    if f.version != 2 or f.dir != FROM_ESP: return
    if f.fmt != SIGN and f.fmt != CHANNEL_FORMAT: return
    if not session:
        first = first_message(f.data)
        if f.fmt != SIGN or first.fId != BEACON: return
        b = parse_beacon(first) or return
        k = keys[b.sn] or return report_unknown(b)
        if not verify_esp(f, k): return
        connect(f, b, k); return

    data = open_esp_frame(f, key) or return          // тег
    if f.iv[3] != esp_instance: return
    if f.iv[8..11] != esp_session:                   // другой сеанс ESP
        first = first_message(data)
        if first.fId == BEACON: connect(f, parse_beacon(first), key)
        return
    if N(f.iv) <= esp_rx: return
    esp_rx = N(f.iv); last_rx = now()

    for m in split(data):                            // разбор по len
        if size(m) < MIN_LEN[m.fId]: continue
        switch m.fId:
            BEACON: interval = parse_beacon(m).interval
            ACCEPT: accepted = true; subscribe_all()
            PING:   send(build_frame(CHANNEL_FORMAT, pack([[0x05]])))
            else:   app.on_message(m)

connect(f, b, k):
    key = k; esp_instance = f.iv[3]; my_instance = esp_instance ^ 0xFF
    esp_session = f.iv[8..11]; tx = esp_rx = N(f.iv)
    random = secure_random(4); interval = b.interval; last_rx = now()
    session = true; accepted = false
    send(build_frame(CHANNEL_FORMAT, pack([[0x01]])))

// ---------- таймер, например раз в 250 мс
on_tick():
    if session and now() - last_rx > 3 * interval: session = false   // к поиску
```

## 11. Чек-лист

- [ ] Векторы V1–V8 совпадают байт в байт.
- [ ] DATA_MAX клиента = DATA_MAX канала ESP; MSG_MAX = min(DATA_MAX − 1, 255).
- [ ] LEN записан в заголовок до подписи: заголовок входит в AAD.
- [ ] В конце AAD своих кадров — сеанс ESP; в кадрах ESP его нет.
- [ ] SIGN: DATA в AAD; ENCRYPT: DATA в шифр. За IV в ENCRYPT — шифротекст, затем тег.
- [ ] CTRL0 клиента = 0x82; instance клиента = instance ESP XOR 0xFF из beacon.
- [ ] N в 64-битном целом, перенос counter в epoch работает.
- [ ] Сеанс проверяется раньше N; другой сеанс в beacon — переподключение.
- [ ] accept — сразу после beacon; прикладные данные — после accept от ESP; после accept — подписаться заново.
- [ ] На ping — ответ сразу, не дожидаясь приложения.
- [ ] Перед каждым сообщением в DATA — его len; неизвестный fId пропускается; короткое сообщение отбрасывается, разбор продолжается.
- [ ] Связанные сообщения упакованы в один кадр.
- [ ] random и ключи — из криптостойкого генератора/хранилища; ключ не попадает в логи.

## 12. Что не описано

- Когда ESP шлёт ping и когда закрывает сеанс без ответа — решает ESP; клиенту достаточно отвечать на ping и следить за 3 × interval.
- Список объектов CAN, их типы значений и параметры блоков зависят от устройств — это описание конкретной машины, а не протокола.

## 13. Тестовые векторы

Кадры клиента и ESP собраны двумя независимыми реализациями; каждая проверила кадры другой, в том числе отказ подписи при чужом сеансе.

Общие данные:
- ключ: `00 01 02 … 1f`;
- ESP: instance 0x01, epoch 1, сеанс `a1 b2 c3 d4`, SN `01 … 08`, имя «ECU», interval 5000;
- клиент: instance 0xFE, random `11 22 33 44`;
- DATA_MAX 128; формат SIGN, кроме V8.
