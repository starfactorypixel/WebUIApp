# WebUI — архитектура и решения

Этот файл для того, кто продолжает работу над проектом, будь то человек или ИИ в новом чате. В нём описано, **как устроена система и почему именно так**. Справочник настроек виджетов — `js/client/widgets/WIDGETS.md`, протокол с ESP32 — `PROTOCOL_SERVER_ESP.md`, скрипты в этом проекте — `SCRIPTS_PROTOCOL.md`.

> Состояние на 26.10.2026. При расхождении с кодом **прав код**: обновите этот файл.

---

## 1. Что это

Веб-интерфейс для мониторинга, управления и настройки блоков на шине CAN.

```
Блоки (CAN) ⇄ ESP32 (шлюз, хранит последнее состояние каждого obj)
          ⇄ UART, протокол L3 (подпись/шифрование AES-GCM)
          ⇄ server.js (Node) ⇄ WebSocket ⇄ браузер
```

Три страницы в браузере на общих модулях:
- **`client.html`** — рабочий интерфейс: вкладки с виджетами (`<ui-element>`), значения obj и команды.
- **`config.html`** — настройка блоков: информация о блоках и чтение/запись их параметров по описанию из `data/blocks.json`.
- **`scripts.html`** — редактор скриптов ESP32 (DrakeScript): чтение, запись, удаление, перезагрузка; дизассемблер по `data/drake_script.json`.

## 2. Главные правила (нарушать нельзя)

1. **Никаких запросов «по одному».** Что относится к одному действию, браузер отправляет одним WS-сообщением: подписку и отписку вместе (`CanSub`, очередь в `client/subscriptions.js`), команду многообъектного виджета и групповое чтение настроек (`WSSendCanMsgBatch`). Сервер кладёт одно WS-сообщение в минимум пакетов L3. Подписка по одному id роняла систему.
2. **Упаковка — забота только сервера.** Браузер не знает размеров пакетов L3; сервер считает, сколько сообщений помещается в сообщение L3 (`l3.msg_max`), из длины заголовка и элемента (без «магических» 31/32).
3. **Простота важнее «правильности».** Автор должен понимать и уметь поправить любой кусок. Однажды клиентская часть уже была переписана с 722 строк на 436, потому что стала непонятной. Перед добавлением абстракции стоит спросить себя, можно ли обойтись без неё.
4. **Повторов команд нет.** Если устройство не ответило, это показывается пользователю, решение остаётся за ним.
5. **На экран — то, что нужно пользователю; ошибки настройки виджетов — только в консоль** (раздел 9).
6. **Ручное указание obj у каждого виджета сохраняется.** Виджеты с нестандартной логикой подписываются сами, на любые obj.
7. **Сервер не должен падать от запроса браузера.** Обработка команд WS обёрнута в `try/catch` (`HandleWSCommand`).
8. **`app-*.js` — только связка.** Входной файл страницы импортирует модули, создаёт компоненты на элементах страницы, соединяет их события и вызывает `WSStart()`. Логика — в модулях папки страницы (`client/`, `config/`, `scripts/`). Адрес сервера — один, в `utils/ws.js`.
9. **Стиль кода:** табы, `if(` без пробела, фигурные скобки на новой строке (Allman), комментарии на русском, `escapeHtml` для всего, что из config попадает в `innerHTML`.

## 4. Протокол WebSocket (браузер ⇄ server.js)

Все сообщения — JSON `{ cmd, data }`.

**Браузер → сервер**

| cmd | data | Что делает сервер |
|---|---|---|
| `CanSub` | `{sub: [id, ...], unsub: [id, ...]}` (сколько угодно) | запоминает и снимает за клиентом; в ESP — L3 `CanSub` (0x12): `[fId][count][id u16]×count`, у отписки бит `0x8000`. Отписка (только obj, не нужные больше никому) и подписка — в одних и тех же сообщениях, сначала отписка, всё одним пакетом (или минимумом пакетов) |
| `CanMsg` | `{id, bytes}` | одно сообщение L3 `CanMsg` (0x35): `[fId][id u16][len][bytes]` |
| `CanMsg` | `[{id, bytes}, ...]` | группа: все сообщения упаковываются в минимум пакетов L3 |
| `Raw` | `{bytes}` | одно сообщение L3 как есть: `[fId][данные…]` |
| `ScriptLoad` / `ScriptSave` / `ScriptDelete` / `ScriptReload` / `ScriptList` / `ScriptEnable` | см. `SCRIPTS_PROTOCOL.md` | операции со скриптами ESP; обмен с ESP по частям ведёт сервер, ответ — только запросившему |

Каждая WS-команда — `add()` всех её сообщений и один `commit()`: что пришло одной командой, уходит вместе.

**Сервер → браузер**

| cmd | data | Кому | Событие в `ws.js` |
|---|---|---|---|
| `CanMsg` | `{id, bytes}` | **только клиентам, подписанным на этот obj** | `packet` {id, bytes} → `subscriptions.js` → виджеты |
| `Raw` | `{bytes}` | всем | `packetRaw` {bytes} (например, информация о блоке, fId 0x0A) |
| `Script*Resp`, `ScriptProgress` | см. `SCRIPTS_PROTOCOL.md` | только запросившему | `response` {cmd, data} |

Функции отправки в браузере: `WSSendCanMsg(id, bytes)`, `WSSendCanMsgBatch([{id, bytes}, ...])`, `WSSendRaw(bytes)`, `WSCanSub(sub, unsub)`. Без связи они возвращают `false`: команды **не копятся**, иначе нажатие могло бы сработать на железе через минуту.

## 5. Протокол объектов CAN (байты в `CanMsg.bytes`)

Первый байт — **всегда fId** (пришёл «как есть» из CAN; в `PROTOCOL_SERVER_ESP.md` он называется CAN-fId, чтобы не путать с fId сообщения L3). Числа little-endian.

| fId | Направление | Смысл |
|---|---|---|
| `0x61` / `0x62` / `0x63` | от блока | Периодическая отправка по таймеру; тип таймера уже классифицирует значение: норма / предупреждение / критично (по наихудшему) |
| `0x65` | от блока | Текущее (новое) состояние. Ответ на **любую** команду и на **подписку**. Без классификации |
| `0xE6` | от блока | Ошибка объекта. Пока не реализовано ни на блоках, ни на сервере |
| `0x01 value` | к блоку | SET — установить значение |
| `0x02` | к блоку | TOGGLE — блок сам решает, во что переключить (обычно 0x00 ⇄ 0xFF) |
| `0x03` | к блоку | ACTION — однократное действие |
| `0x11` | к блоку | запрос всех значений `stream` (кнопка ⟳ или автозапрос по `interval`) |
| `0x0A counter value` | к блоку | RealTime — «живое» управление (`livecontrol`): пока держат, каждые `interval` мс; `counter` uint8 своего obj, +1 на пакет. Ответа нет |
| `0x37 cmd id [value]` | ⇄ | настройка параметров блока (config.html), см. раздел 11 |

**Поведение объектов:**
- **Управляемые** (например, «включить фары») шлют пакет только в ответ на команду или подписку.
- **Индикаторы** (например, напряжение) шлют пакеты по таймеру.
- **Самосинхронизация:** в ответ на подписку шлюз присылает последнее известное состояние obj. Поэтому повторная подписка безвредна и используется как способ получить состояние.

## 6. Сервер (`server.js`, `L3Packet.js`)

- **UART** открывается и переоткрывается сам (раз в секунду), например если USB-UART отвалился или его ещё нет.
- **L3** — сеансовый протокол с ESP32, полностью описан в `PROTOCOL_SERVER_ESP.md`. Кратко: сервер ждёт beacon, проверяет подпись ключом по SN (`server.json → l3.keys`), отправляет accept; сеанс открыт, когда ESP ответит своим accept. Потеря связи (> 3 интервалов beacon), смена сеанса ESP или закрытие порта — и сервер сам ждёт beacon заново. DATA ≤ `l3.data_max` (сейчас 128, **как у ESP**; кадр ESP длиннее отбрасывается с ошибкой в логе `[l3]`) — сообщения подряд, перед каждым его длина: `[len u8][fId][данные…]`. Длину пишет `l3.add()`, снимает `_dispatch()`: в `message` приходит сообщение без `len`. Сообщение — не больше `l3.msg_max = min(data_max − 1, 255)`, от него считаются все размеры.
- `l3.add(msg)` + `l3.commit()` — сообщения подряд в пакет; `l3.send(msg)` — одно сообщение отдельным пакетом (так шлёт запросы `server/scripts.js`). Без сеанса отправка не выполняется (пишется в лог).
- **Приём:** `data/l3_fids.json` задаёт для каждого типа `fid` и `min_length` — сколько байт (с fId) нужно обработчику, чтобы прочитать свой заголовок. Сообщение короче отбрасывается с записью в лог, остальные сообщения пакета разбираются дальше; обработчики длину не проверяют. Типы, которых нет в `l3_fids.json`, уходят браузерам как `Raw`.
- **Порт WS занят** (обычно — сервер уже запущен): в лог `[ws] ОШИБКА: порт 8080 занят — сервер уже запущен?` и выход с кодом 1. Ошибки COM-порта сервер не роняют: «не открыт: …» в лог и повтор раз в секунду.
- **Подписки по клиентам.** Сервер хранит набор obj каждого WS-клиента (`clientSubs`). Четыре правила:
  1. подписка от клиента **всегда** уходит в ESP (повторная безвредна, ESP ответит состоянием);
  2. отписка уходит в ESP, только если obj больше не нужен ни одному клиенту;
  3. клиент закрыл WS — его obj снимаются по правилу 2;
  4. L3 `connect` (ESP перезапустился, отвалился USB) — подписка на объединение obj всех клиентов.
- **Упаковка:** `SendCanSub` делит id (отписку и подписку вместе) на сообщения по `(msg_max − заголовок) / размер id` и кладёт их через `add()` + `commit()`; `CanMsg` — так же. Размеры заголовков — именованные константы в начале `server.js`.
- **Лог** (`logcmd.js`) копит строки и пишет пачкой раз в 50 мс, потому что консоль Windows медленная. Источники: `[server]`, `[serial]`, `[ws]`, `[l3]`. Отладочные флаги — в `server.json`.

## 7. Клиент: виджеты и подписки

**Запуск** (`app-client.js`): регистрация классов → события вкладок → `new Tabs()` (открывает первую вкладку) → виджеты вне вкладок → `WSStart()`. Порядок не важен: подписки, сделанные до открытия сокета, уйдут при `open`.

**Жизнь виджета:**
1. `dispatch.initWidgets(panel)` при `tab:open` читает `type`, `obj` (hex, можно список через запятую, если у класса `static multiObj = true`), `config` (JSON) → `new Cls(el, config, ids)` → `Render()`.
2. В `Render()` виджет строит HTML и **сам явно** вызывает `this.Subscribe()` (свой obj → `Update`) или `this.Subscribe(id, handler)`.
3. Пакет: `ws.js` → `packet` → `subscriptions.js` → все обработчики этого obj → `Update(bytes, id)`.
4. `dispatch.deinitWidgets(panel)` при `tab:close` → `Destroy()`. Базовый `Destroy()` снимает подписки; наследник со своими ресурсами (график, `Control`) переопределяет его и вызывает `super.Destroy()`.

**В `UIWidget`:** `this.ids` / `this.id`, `this.refs`, `ReadValue(data, offset=1)` → `{value, value_raw}` (`null` при коротком пакете), `AutoColor(fId)`, `this.timer_type` (`0x61→normal`, `0x62→warning`, `0x63→critical`).

**Подписки (`subscriptions.js`):**
- `subscribe(id, fn)` кладёт id в очередь подписки (**на каждого нового подписчика**: шлюз ответит состоянием) и возвращает функцию отписки.
- Ушёл **последний** подписчик obj → id в очередь отписки.
- Очередь уходит в конце текущей задачи (`queueMicrotask`) одним WS-сообщением `CanSub {sub, unsub}`, сервер отправляет его в ESP одним пакетом. Вкладка создаёт все виджеты за одну задачу. Obj, нужный и старой, и новой вкладке, не отписывается.
- WS открылся (первый раз или после обрыва) → `CanSub` с подпиской на все obj. Нет связи → ничего не отправляется.

## 8. Управляемые виджеты (`control.js`)

`button`, `radio`, `range` работают через `Control`; виджет только рисует.

- **Поля:** `values` (obj → последнее значение), `waiting`, `answers`, `target` (значение SET), `failed`, `notSent`.
- **Команда:** `set(v)` / `toggle()` / `action()` → одним `WSSendCanMsgBatch` во все obj (сервер кладёт их в один пакет L3) и таймер (`Control.timeout` = 1100 мс, у виджета `config.timeout`) → каждый `0x65` вычёркивает obj из `waiting` (для SET ответ должен быть равен `target`, иначе obj в `failed`) → ответили все или вышло время → `finish()`. Пока ждём ответ, виджет заблокирован. `failed` очищается следующей командой.
- **Лог отклонений** (одна строка на команду, только если что-то не так):
  `[КПП М1+М2] SET 8: 0x0106=8, 0x0107=4` · `[Выход 2] TOGGLE: 0x0165=нет ответа` · `[Выход 1] TOGGLE: 0x0164=не отправлено`
- **Отображение:** `value` (общее значение или `null`), `mixed`, `busy`, `showState(el)` → `is-pending` / `is-mixed` / `is-failed` + подсказка.
- **button:** один obj → TOGGLE; группа → SET («все равны `on` → `off`, иначе → `on`»). **radio:** клик не ставит отметку, её ставит только подтверждение. **range:** SET по `change` (отпустили или стрелка на клавиатуре).
- **Ограничение:** протокол не говорит, на что пришёл `0x65`. Одновременное ожидание у двух виджетов с общим obj может засчитать ответ не той команде. Решено не обрабатывать.

**Шаблон своего управляемого виджета:**
```js
Render():  this.control = new Control(this.ids, this.config, () => this.Show());
           for(const id of this.ids) this.Subscribe(id);  this.Show();
Update(data, id):  this.control.onPacket(id, data);
клик:      this.control.set(v) / toggle() / action()
Show():    рисуем control.value / busy / mixed; this.control.showState(this.element);
Destroy(): this.control.destroy(); super.Destroy();
```

## 9. Лог в браузере (`utils/loghtml.js`)

`log.info / warn / error(текст, ...доп)`: текст идёт на экран (`#log`, `ЧЧ:ММ:СС`, последние 200 строк) и в консоль; доп. аргументы — только в консоль.

| Куда | Что |
|---|---|

| Только консоль | `[Виджеты]` ошибки разметки и config; неизвестный оператор в `expr`; `[drake_script.json]` ошибки описания команд |

## 11. Режим настройки (`config.html`)

**Как работает:**
1. Каждый блок раз в ~5 с присылает пакет информации (`Raw`, fId `0x0A`, 32 байта). `BlockInfo` рисует карточку на каждый `baseID`: имя типа из `blocks.json`, версии, SN, uptime, напряжение, ток, температура, флаги ошибок. Тип, которого нет в `blocks.json`, подписан красным; карточка с ненулевыми флагами ошибок — розовая.
2. Клик по карточке → `BlockParams.Open(info)`:
   - параметры берутся из `blocks.json → blocks[type == hw_type].params` и рисуется список (номер, имя, описание, поле с `min/max/step`, кнопки «прочитать / записать / по умолчанию»);
   - obj настроек = `baseID + blocks.json → offset`; на него оформляется подписка через `subscriptions.js`;
   - сразу после подписки — **групповое чтение всех параметров одним WS-сообщением** (`WSSendCanMsgBatch`), сервер упакует его в минимум пакетов L3.
3. Выбор другого блока или ✕ → `Close()`: отписка от obj настроек, таймеры сняты. Закрытие браузера — отписку делает сервер.
4. WS переподключился → подписка восстанавливается сама, открытый блок перечитывается.
5. Поле блокируется на время запроса. Нет ответа за 1,1 с — поле разблокируется, строка получает `is-failed`, в лог: `[Настройки 0x0161] Параметр 5 «Время порт 5»: нет ответа`.

**Пакеты настроек** (fId `0x37`, obj настроек; value — по `type` параметра, little-endian):

| Запрос | Ответ | Смысл |
|---|---|---|
| `0x37 0x01 id` | `0x37 0x01 id value` | чтение |
| `0x37 0x02 id value` | `0x37 0x02 id [value]` | запись (если блок вернул value — оно показывается) |
| `0x37 0x03` | `0x37 0x03` | сохранить всё и перезагрузить: кнопка в шапке панели, с подтверждением; ответ или его отсутствие (блок мог перезагрузиться раньше) — в лог |
| — | `0x37 0x04 code` | ошибка (в лог; номера параметра в ответе нет) |

Коды пакетов — константы в `blockparams.js`; шаблоны `blocks.json → packets` пока не используются.

## 11а. Редактор скриптов (`scripts.html`)

- **ID** — hex 0…7FF (2048 скриптов в ESP). Скрипт — до 4080 байт (сектор 4 КБ минус заголовок 16 байт).
- **Редактор** — текст с hex-байтами, комментарии `//`, `/* */`, `#`, `;` допускаются. Файлы `.drs` — тот же текст.
- **Дизассемблер** (`disasm.js`): на каждую команду строка `// адрес Имя(аргументы)` и её байты. Описания — в комментариях, поэтому разобранный текст можно сразу записать обратно. Кнопка «Разобрать» приводит любой текст к этому виду. **Разбор идёт так же, как исполнение на ESP, и ничего не «чинит»:** первая ошибка (неизвестный опкод, обрезанная команда, регистр или значение enum, которых нет в JSON, значение вне `min`/`max`) останавливает разбор, остаток выводится сырыми байтами с одной строкой «ОШИБКА … дальше не разобрано». После разбора проверяются переходы: поле `jump` должно указывать на начало команды. Под редактором — сводка: байты, команды, первая ошибка разбора с адресом, превышение размера; перед записью скрипта с ошибкой — отдельное подтверждение. `drake_script.json` проверяется при загрузке (`length` = опкод + поля, известные типы и enum) — ошибки в консоль.
- **Список «В памяти ESP»** слева: скрипты, загруженные в PSRAM, то есть то, что исполняется. ID, размер, галочка «включён». Клик по строке — прочитать скрипт в редактор (из памяти ESP). Галочку ставит только ответ ESP; отключённые — серым. Список обновляется при подключении и после записи, удаления, перезагрузки.
- **Запись и удаление** меняют только флеш-память. Пока не нажата «⟳ Перезагрузить все скрипты», исполняются старые скрипты, а над списком — оранжевая подсказка «Флеш-память изменена — …» (признак `reload_needed` от ESP).
- **Операции** — одна за раз, кнопки заблокированы до ответа сервера (поле `error` — ошибка в лог). Во время чтения и записи под редактором — прогресс в байтах. Запись (с предупреждением, если ID занят) и удаление — с подтверждением.
- **Протокол с ESP — `PROTOCOL_SERVER_ESP.md`, раздел 9** (реализация в проекте — `SCRIPTS_PROTOCOL.md`): источник правды — память ESP (PSRAM), ответ на любой запрос, коды ошибок, смещения вместо номеров кусков, CRC-32 в конце записи и при чтении, размеры от `msg_max` (ESP сообщает свой лимит куска), постраничный список с `reload_needed`. Ожидание шага — 1,1 с, RELOAD — 5,5 с. Серверная сторона — `js/server/scripts.js`, сторона ESP — `esp/ScriptProto.h` (что доделать на ESP — в конце `SCRIPTS_PROTOCOL.md`).

## 12. Открытые вопросы и известные проблемы

1. **ESP: one-shot-subscribe не удаляется.** Ответ на запрос к неподписанному obj оформляет в ESP временную подписку, которая остаётся навсегда (известный баг прошивки). `config.html` теперь подписывается на obj настроек явно и отписывается при закрытии — со стороны интерфейса всё чисто.
2. **Отписка от неизвестных ESP obj.** Сервер рассылает отписку только по своим данным; one-shot-подписки из п.1 он не видит и не снимает.
3. `Raw` из браузера уходит в ESP без проверки: любая открытая страница может отправить что угодно.
4. Скрипты: если ответ ESP придёт уже после таймаута шага, он может быть принят следующим запросом с той же командой. На практике это возможно только при очень медленной флеш-памяти; при появлении — добавить в ответ номер запроса.
5. Структура пакета `cellbalance` (7 байт без выравнивания, `val` в мВ) и нумерация ячеек не сверены с прошивкой.
6. Проверки живости WS (ping) в браузере нет: зависшее соединение может обнаружиться не сразу.
7. **ESP: смешанное сообщение CanSub** (часть id с битом отписки 0x8000, часть без) сервер шлёт при каждой смене вкладки. Что обработчик ESP это понимает — не проверено на железе.
8. **ESP: `esp_crc32_le`** должен совпадать со стандартным CRC-32 (`"123456789"` → `0xCBF43926`); на железе не проверено (`SCRIPTS_PROTOCOL.md`).

## 13. Отвергнутые решения (не возвращаться без причины)

| Было / предлагалось | Почему отказались |
|---|---|
| Подписка по одному id на каждый виджет | Падала система. Браузер шлёт всё одним WS-сообщением, сервер делит по размеру пакета L3. |
| Деление на 32 в браузере, «магические» 31/32 | Упаковка — особенность протокола ESP, её делает только сервер, размеры считаются из констант заголовков. |
| Режим упаковки + отдельная команда «отправить накопленное» | Не нужно: массив в `CanMsg.data` — это пакет, конец WS-сообщения — commit. |
| Очередь в `ws.js`, неявно склеивающая все `WSSendCanMsg` одной задачи | Отправитель сам решает, что уходит группой (`WSSendCanMsgBatch`) — это видно в коде. |
| `try/catch` вокруг обработчиков сообщений L3 | Вместо него `min_length` в `l3_fids.json`: короткое сообщение не доходит до обработчика. Падение обработчика после этого — ошибка в коде, её должно быть видно. |
| `obj-group.js`: статусы `partial`/`unknown`, снятие ошибки поздним ответом, счётчики «1/2» у радио | Слишком сложно, автор перестал понимать код. Заменено на `control.js`. |
| Вычисление разницы «что знает сервер» в браузере | Сложно. Заменено на очередь + «отписка, только если подписчиков не осталось». |
| Кэш последнего пакета для новых подписчиков | Повторная подписка проще: шлюз сам пришлёт состояние. |
| Атрибут `id` (и `data-*`) для адреса | `id` должен быть уникален в HTML, `data-*` автор не хочет. Выбран `obj`. |
| Оптимистичная отметка радио при клике | Показывала бы неподтверждённое состояние. |
| Отдельная таблица уровней в виджете | Есть `this.timer_type` в `UIWidget`. |
| Имена `level`, `cells` | Непонятны. Стали `autocolor`, `cellbalance`. |

## 14. Как проверялось

Тестовые стенды лежат вне проекта (в рабочей папке сессии); здесь — что именно проверено.

- **Браузер, имитация сервера:** WebSocket-сервер на Python + headless Chromium (Playwright): старт без сервера, подписки одним сообщением, смена вкладок, группы кнопок, радио и ползунков, таймауты, лог, переподключение, autocolor, cellbalance, stream, config.html (карточки, групповое чтение, запись, таймаут параметра, переключение блоков, закрытие), scripts.html (операции, блокировка кнопок, дизассемблер).
- **Настоящий `server.js` + заглушка ESP, браузер:** открытие страницы — подписка одним пакетом L3; каждая смена вкладки — **один** пакет с отпиской и подпиской; кнопка на два obj — один пакет с двумя CanMsg; значения приходят на новую вкладку; второй запуск сервера — ошибка «порт занят» и код 1.
- **Слой кадров:** настоящий `L3Packet.js` и кадры ESP с настоящей подписью: beacon → accept → подключение, DATA до `data_max`, сообщение `msg_max`, отправка с переходом на новый пакет, кадр длиннее `data_max` — ошибка в логе, расхождение `data_max` с ESP, `min_length` (короткое сообщение отброшено, остальные дошли).
- **Тестовые векторы** `PROTOCOL_SERVER_ESP.md`: кадры сервера собраны `L3Packet.js`, кадры ESP — отдельной реализацией на Python; каждая сторона проверила кадры другой (SIGN и ENCRYPT, отказ подписи при чужом сеансе).
- **Скрипты:** `esp/ScriptProto.h` собран на ПК при DATA 64, 128 и 300 с функциями флеш-памяти из `ScriptLogic.h` и настоящей картой скриптов библиотеки DrakeScript (с правками `IsLoaded`, `always`); против него — серверный модуль, несколько сообщений в одном пакете, ENABLE/RELOAD, и браузерный тест страницы скриптов с настоящим `server.js`.
- **Не проверялось на железе:** весь C++ код ESP, смешанный CanSub на ESP, `esp_crc32_le`.
